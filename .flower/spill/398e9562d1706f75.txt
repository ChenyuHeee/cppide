### 0.1 先验证"验证工具"本身可信

审计前先对 pty 驱动器做了**正负控**,避免拿一个"永远 PASS 的假机器"去审计:

```
负控:expect ZZZ_NEVER_APPEARS_ZZZ  -> 退出码 1(== 有失败 ==)  ✅ 会失败
正控:expect cppide                 -> 退出码 0(== 全部通过 ==)✅ 会通过
```

**驱动器的一个坑(踩了,记下来)**:`wave5-pty-drive.cpp` 的第 4 个参数名叫 `raw_out`,
但它写进去的是**过滤掉转义序列后的文本**(`g_plain`,第 592–593 行);
**真正的原始字节流在 `<raw_out>.raw`**(第 594–595 行)。
一开始拿错文件去抓 ANSI 属性,得出"全部 token 同色、没有高亮"的假结论。
凡是要断言颜色/属性的,必须用 `.raw` 那个文件。

### 0.2 两类会制造假失败的断言陷阱(本次踩到,已在脚本里注释固化)

1. **ncurses 是差量重绘**。状态栏从 `1:1` 变成 `12:23` 时,ncurses 只重写发生变化的格子,
   过滤后的流里会残留成 `2:23`,看起来像"跳错了行"。
   → 凡是断言光标落点,**一律走文件系统**(在落点敲一个标记、存盘、看标记在第几行)。
2. **逐字符回显**。连续敲 `ZZALIVE1`,每个字符各触发一次重绘,过滤后字符之间被插入空格,
   `expect "ZZALIVE1"` 永远匹配不上。
   → 凡是断言"输入生效",**一律走文件系统**(存盘后 grep)。

本报告里凡标注"文件系统断言"的证据,都不受这两个陷阱影响。

### 验收 7 — 练习模式:同一 AI 入口不插码;只在独立面板输出中文思路;Tab 不接受 AI 内容

4. 边界加测:**写代码模式先拿到一个活的 ghost,再 `Ctrl-T` 切到练习模式,然后按 Tab**。

**是不是结构性保证?是。** 我按"AI 文本能不能到达 `TextBuffer::insert`"这条线独立追了一遍:

   `onAiDelta`(`app.cpp:559`)刻意**不落地**,只累加到 `ai_stream_`。

   if (ghost_.text.empty())              return false;
   if (ghost_.sink != AiSink::GhostText) return false;   // ★ 结构性拦截

   `setGhost()`(第 650 行)除 assert 外还有一条**运行期** early-return —— NDEBUG 下
   assert 被裁掉后仍然拦得住,退化方向永远是"没有 ghost",不可能是"代码被插入"。
4. **`doTab()`(`app.cpp:892-903`)里一行模式判断都没有** —— 它不需要,因为练习模式
   永远拿不到 ghost。这正是"结构性"的含义:不靠记得处处判模式。

我特意找过有没有第二条插入路径:`ai.cpp` / `aihttp.cpp` / `ui.cpp` 都不持有可写 `TextBuffer&`;

## 3. 本次审计新发现的问题(按严重度排序)

### 问题 1 【P1 · 花钱】写代码模式空转会无限重复发请求

**位置**:`src/ai.cpp:203-215`(`AiService::maybeAutoTrigger`),调用点 `src/app.cpp:189`(每 tick 一次)

**现象**:切到写代码模式、敲一个字符之后**完全不碰键盘**,请求不会停。

**实测**(`audit-idle-cost.sh`,全默认配置):
```
配置:全默认(ghost_delay_ms=500,ghost_min_interval_ms=1200)
操作:切到写代码模式 -> 敲 1 个字符 -> 之后 20 秒完全不碰键盘
结果:服务端收到 23 次 chat/completions 请求
折算:约 69 次/分钟,约 4140 次/小时
```

**根因**:`maybeAutoTrigger` 只有两个**时间**阈值:
```cpp
if (now - last_activity_ms_      < cfg_.ghost_delay_ms)        return;
if (now - last_auto_request_ms_  < cfg_.ghost_min_interval_ms) return;
```
`last_activity_ms_` 只在 `noteActivity()` / `setMode()` 里更新。用户不动键盘时它就不再前进,
于是第一个条件**永远满足**;第二个条件每过 `ghost_min_interval_ms` 就再次满足。
缺的是一个"**本次停顿已经请求过了**"的状态位(或"已有 ghost 就不再请求"的判断)。

**影响面**:ICPC 训练场景下,把编辑器挂在写代码模式去想题、去吃饭、切到别的窗口,
都会持续计费。这是需求"省钱"意图(`ghost_min_interval_ms` 的注释与 README §5.2 都写了"省钱")
**没有真正达成**的地方 —— 它只限了频率,没有限总量。

**为什么我没有直接改**:最小修法要在 `AiService` 里加一个状态位(如
`std::atomic<bool> auto_done_since_activity_`),`noteActivity()`/`setMode()` 里清零、
`maybeAutoTrigger()` 里置位并判断。这要动 `src/ai.h` —— 而 `.flower/notes/跨模块约定.md §0`
明确规定 **`src/*.h` 已冻结,任何字段变更必须由协调者统一改**。故只报告,不动手。

**建议**:约 4 行改动(1 个成员 + 2 处清零 + 1 处判断),由协调者裁决后落地。
同时建议 README §5.2 把这个行为写清楚。

### 问题 2 【P2 · 构建】`make debug -j<N>` 存在竞态,会间歇性链接失败

**位置**:`Makefile:70-72`
```make
debug: CXXFLAGS += -O0 -g -fsanitize=address,undefined
debug: LDFLAGS  += -fsanitize=address,undefined
debug: clean all
```

**现象**:`clean` 和 `all` 是**两个平级的先决条件**,GNU Make 在 `-j` 下可以并发执行它们。
于是 `clean` 会在 `all` 已经编出一部分 `.o` 之后把它们删掉,链接阶段报文件不存在。

**实测**(本次审计真踩到):
```
$ make debug -j4
g++ … -c -o src/aihttp.o src/aihttp.cpp      # 注意:ai.o 从头到尾没被编译
…
g++ -fsanitize=… -o cppide src/ai.o src/aihttp.o …
/usr/bin/ld: cannot find src/ai.o: No such file or directory
collect2: error: ld returned 1 exit status
make: *** [Makefile:51: cppide] Error 1
```
**是竞态不是必现**:同一条命令重跑一次就过了(`make debug -j4` → `exit=0`)。
串行 `make debug` 稳定成功。

**影响面**:任何人用 `make debug -j` 跑 sanitizer 验证时,会随机撞到一次假的"编译失败",
而且失败形态(`cannot find src/ai.o`)极具误导性 —— 看起来像源码/依赖出了问题。
**更糟的是它会把 `./cppide` 删掉**,如果此时有别的验收脚本正在用这个二进制,会被连带打挂
(本次审计就发生了:README 快捷键那一轮因此整轮作废,重跑才拿到结果)。

**建议修法**(递归 make,保证顺序):
```make
debug:
	$(MAKE) clean
	$(MAKE) CXXFLAGS="$(CXXFLAGS) -O0 -g -fsanitize=address,undefined" \
	        LDFLAGS="$(LDFLAGS) -fsanitize=address,undefined" $(BIN)
```
**为什么我没有直接改**:这改变了 `debug` 目标的实现方式(目标特定变量 → 递归 make),
属于构建系统的结构性改动,且 Makefile 由协调者统一维护。只报告。
临时规避:`make debug` 不加 `-j`。
