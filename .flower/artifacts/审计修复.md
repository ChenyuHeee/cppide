## 1. P1 —— 写代码模式空转无限重发请求(花钱)

### 修法

`AiService` 私有区新增(`src/ai.h`):

```cpp
static constexpr uint64_t kNoAutoGen = ~static_cast<uint64_t>(0);
std::atomic<uint64_t> auto_done_gen_{kNoAutoGen};
```

语义:**记录"上一次自动请求是针对哪一个活动 generation"**。`gen_` 只在用户又有活动时前进,
所以"同一次停顿只请求一次"= "同一个 `gen_` 只自动请求一次"。四处配合(全在 `src/ai.cpp`):

| 位置 | 动作 | 为什么 |
|---|---|---|
| `maybeAutoTrigger()` | `if (auto_done_gen_ == gen_) return;` 发之前 `store(g)` | 额度只有一份 |
| `noteActivity()` | 不动(它自增 `gen_`,天然重新开额度) | 打字/移动光标 = 新活动 = 允许下一次 |
| `setMode()` | `store(gen_)`(**不**开额度) | 按 Ctrl-T 不该白花一次钱 |
| `cancelInFlight()` | `store(gen_)`(**不**开额度) | Esc 丢弃 ghost 后不该把同一份建议再买一遍 |
| `askNow()` | `store(gen_)`(手动本身不受任何限制) | 手动问过了不必再自动补一发 |

### 实测(`.flower/scripts/fix-p1-idle-verify.sh`,可重复跑)

pty 里指向本地假端点,全部用内置默认值(`ghost_delay_ms=500`、`ghost_min_interval_ms=1200`):

```
改前(audit-idle-cost.sh,20 秒空转)       : 23 次   ≈ 69 次/分钟
改后(纯 30 秒完全不碰键盘)                : 1 次    ← 断言 == 1
改后(30 秒空转 + 打 1 个字符 + 再等 12 秒) : 2 次    ← 断言 == 2
ghost 仍然正常显示(屏幕上出现 GHOSTMARK)  : PASS
pty 驱动退出码                              : 0
```

同一脚本在 ASan/UBSan 版二进制(`CPPIDE_BIN=/work/cppide-debug`)下再跑一遍:同样 1 / 2 次,
**零 sanitizer 报告**。

顺带把审计员的复现脚本 `audit-idle-cost.sh` 也重跑了:`结果:1 次` → `PASS`。

### 副作用与取舍(需要知道的)

- **AI 报错(500/超时/401)之后也不会自动重试**:额度已被那次请求用掉,要重试就再打字或按 Ctrl-A。
  这是有意的(避免"错误 + 限流"变成烧钱循环),`audit-net-failures.sh` 16/16 仍全过。
- **切模式不再自动触发一次补全**。审计报告的原话是"只有 `noteActivity()` 之后才允许下一次自动请求",
  这里严格照做。若协调者更希望"切到写代码模式立刻来一发",把 `setMode()` 里那行 `store()` 删掉即可
  (代价:纯空转口径会变成 2 次而不是 1 次)。

## 2. P2 —— `make debug -j` 竞态且会删掉 `./cppide`

### 修法(不用递归 make,改成独立产物)

`Makefile`:

```make
DBGBIN   := $(BIN)-debug          # ./cppide-debug
DBGOBJ   := $(SRC:.cpp=.dbg.o)    # src/*.dbg.o
DBGDEP   := $(DBGOBJ:.o=.d)
SANFLAGS := -fsanitize=address,undefined
DBGCXXFLAGS := $(filter-out -O2,$(CXXFLAGS)) -O0 -g $(SANFLAGS)

debug: $(DBGBIN)
$(DBGBIN): $(DBGOBJ)
	$(CXX) $(LDFLAGS) $(SANFLAGS) -o $@ $^ $(LDLIBS)
src/%.dbg.o: src/%.cpp
	$(CXX) $(CPPFLAGS) $(DBGCXXFLAGS) -c -o $@ $<
```

`clean` 连带删 `*.dbg.o / *.dbg.d / cppide-debug`;`-include $(DBGDEP)` 保证 debug 也有头依赖。
**没有动**:Darwin/Linux 分支、`-lncursesw -lcurl -lpthread`、`-Isrc`、`-MMD -MP`、
`SYNFLAGS`/`check-headers`、`tests`、`install`。ASan/UBSan 的编译与链接标志都保留。

### 实测(`.flower/scripts/fix-p2-make-verify.sh`,24/24 PASS)

```
make -j4                      exit=0,warning 0 条
make debug -j4  连跑 3 次      exit=0 / 0 / 0,warning 0 条(竞态是间歇的,故连跑)
./cppide 每次都还在            PASS × 3,且 mtime 未被 debug 构建改动
cppide-debug 带 __asan/__ubsan 符号;./cppide 干净(无 sanitizer)
增量:make -j4 与 make debug -j4 都报 "Nothing to be done"
make check-headers            OK(15 个头)
make tests                    全过
跑完全部目标后 ./cppide 仍在   PASS
```

### 连带改动

`audit-asan-smoke.sh` 原来固定用 `$WORK/cppide` 判断"是不是 sanitizer 版本",现在默认取
`$WORK/cppide-debug`(可用 `CPPIDE_BIN` 覆盖,找不到就回落老路径),否则它会永远"跳过"。

## 4. P4 —— 8 色终端 ghost 的属性

### 事实校正(重要)

`Theme::ghostAttr()` 在改动**之前**就已经是
`if (has_color && colors >= 256 && pairs > P_Ghost) return COLOR_PAIR(P_Ghost); return A_DIM;`,
也就是说 **8 色档本来就走 `A_DIM`,并没有真的把 ghost 画成蓝色**;
审计报告问题 4 是从 `ui.cpp:388` 的 `{P_Ghost, COLOR_BLUE, -1}` 读出来的推断。
那行确实是个**陷阱**(pair 被定义成蓝色,只是恰好没人用),所以照 architecture.md §3 的方案清掉:

- `kPairs` 里 `P_Ghost` 的 fg 从 `COLOR_BLUE` 改为 `-1`(终端默认色,纯占位;256 色档下面会改写成 8);
- `ghostAttr()` / `init_pair` 处各补一条注释,写明"8 色与单色一律 A_DIM,不许用蓝色 ——
  蓝色在 8 色终端上与注释同色,ghost 会被误读成已经写进文件的代码"。

### 实测(`.flower/scripts/fix-p4-ghost-attr.sh`,7/7 PASS)

从 **`.raw` 原始字节流**(不是过滤后文本 —— 审计问题 5 的坑)按 SGR 分段归属
(`fix-sgr-at-marker.py`),抓 ghost 文本 `GHOSTMARK_Alpha();` / `GHOSTMARK_Beta();` 写出时生效的属性:

```
TERM=xterm          (8 色)   -> SGR[0,2]    = 复位 + dim(A_DIM)   ✅ 不含 34/94(蓝)
TERM=xterm-256color (256 色) -> SGR[90]     = 亮黑/灰(color 8)   ✅ 不含 34/94(蓝)
两档 ghost 都真的显示出来;Esc 丢弃后 ghost 没有进文件
```

为此给 `wave5-pty-drive.cpp` 加了 `PTY_TERM` 环境变量(默认仍是 `xterm-256color`),
并在它的用法注释里把"`raw_out` 写的是过滤后文本、真 raw 在 `<raw_out>.raw`"这个坑写死(审计问题 5)。

## 7. 遗留风险 / 未验证

1. **macOS 未验证**:与审计报告 §6 同一风险面。本轮新增的 Makefile `src/%.dbg.o` 模式规则用的是
   GNU make 语法,macOS 自带 `make` 就是 GNU make 3.81,`filter-out`/静态模式都支持;
   但 3.81 上 `debug -j` 我没跑过。
2. **`Config::aiEnabled()` 与 `AiService::enabled()` 语义不同**(前者只看 key)。
   已在 `config.h` 注释里写明。将来若有人拿 `aiEnabled()` 去判"AI 能不能用",会得到偏乐观的答案 ——
   当前全工程只有 `main.cpp` 的 `--doctor` 文案用到它,那两处已单独处理。
3. **P1 的额度语义是"每个 generation 一次"**。`gen_` 也被 `askNow`/`cancelInFlight`/`setMode` 推进,
   我在这三处都主动"关额度";如果以后有人再加一处 `gen_++` 而忘了决定额度归属,
   默认行为会变成"开额度"(可能多发一次请求)。`tests/test_ai.cpp::case_trigger_and_rate_limit`
   能挡住最明显的回归,但它不覆盖"新加的取消点"。
4. **`wave5-verify.sh` 里 B3b 那条 `FAIL`** 是脚本自己 `|| true` 容忍的时序敏感用例,
   与本轮改动无关(它测的是 1.5MB 输出洪流中途的面板刷新),但它每次都会在日志里出现,容易被误读。
5. `fix-p1-idle-verify.sh` 单次要跑 ~90 秒(两轮 30 秒空转),不适合放进快速回归。
