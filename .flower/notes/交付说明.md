## 1. 做出来的是什么

**一个跑在 macOS 终端里的、从零实现的 C/C++ 专用 TUI 编辑器**:ncurses + libcurl + C++17,
内置一键编译/运行(单文件),以及基于 DeepSeek API(OpenAI 兼容 chat completions)的 AI 辅助;
AI 分「练习模式」(只给中文思路,绝不插码)和「写代码模式」(停顿后灰色 ghost text,Tab 接受)两档。

**产物**:仓库根目录的 `./cppide`(单个独立可执行文件,约 600 KB)。
另有 `./cppide-debug`(ASan/UBSan 版,只用于验证,不是交付物)。

**怎么构建**:

```sh
cd /work
make                 # -> ./cppide          (零 warning 是硬要求)
make check-headers   # 每个头文件必须自给自足(Wave 1 验收门)
make tests           # 编译并运行 tests/test_*.cpp
make debug           # -> ./cppide-debug    ASan/UBSan 版,与 release 共存互不删
make clean           # 清掉 *.o / *.dbg.o / 两个可执行文件
```

依赖:`ncurses`(宽字符版)+ `libcurl`。
macOS 系统自带(若有 Homebrew 的 ncurses 则优先);Debian:
`apt-get install build-essential libncursesw5-dev libcurl4-openssl-dev`。

> **构建后请记得 `make clean`**,或至少知道:`make debug` 会在 `src/` 下留一堆 `*.dbg.o`。
> 见下面 §2 的「一个坑」。

**仓库根目录应该只有这些**:`src/`、`tests/`、`Makefile`、`README.md`、`config.sample.json`、
`.flower/`、`cppide`、`cppide-debug`,外加一个 `runs/`。
`runs/`(约 21 MB,内含 `manifest.json` + `sessions.db`)**是开发用 agent 框架自己的会话状态,
不是本项目的构建产物,也不是交付物** —— 它和 cppide 的代码/验证没有任何关系,
真机交付时不需要带上它。
`src/` 下的 `*.o` / `*.dbg.o` / `*.d` 是正常的构建中间产物,`make clean` 一键清掉。
除此之外若看到别的东西,那就是污染。


> **两个坑(都是脚本层的,不是产品问题)**
> 1. **不要在调用命令行里出现 `cppide-` 字样**(比如 `ASANBIN=/work/cppide-debug ... wave5-verify.sh`)。
>    脚本的孤儿进程检查会扫全部 `/proc/*/cmdline` 找 `cppide-`,会把**你自己这条 shell 命令**
>    当成残留进程,报一条假的
>    `FAIL 死循环程序被终止之后:仍有残留进程`。用上面 `cp` 到默认路径的写法就没事。
>    (这条检查本身是有价值的安全网,故意没有放宽它的匹配。)
> 2. `make debug` 之后 `src/` 下会有 `*.dbg.o`。脚本里用 `ls src/*.o` 挑目标文件的地方
>    已经加了 `grep -v '\.dbg\.o$'`(`wave5-verify.sh` 的 `appai`/`openpath` 段、
>    `wave5-finalfix-verify.sh` 的 `test_proc` 段)。**如果以后再写这类链接命令,记得照抄这个过滤** ——
>    否则会得到一片 `multiple definition` + `undefined reference to __ubsan_handle_*`,
>    看起来像单测挂了,其实是选错了 `.o`。

### 关于日志里的 SKIP

`wave5-verify.sh` 的 **B3b(1.5MB 中量输出)**是唯一一条「跑但不计分」的用例:
它的 `expectlast 退出码` 是**末屏时序断言** —— 要求编译运行结束那一瞬间面板末屏正好停在
「退出码 = N」上,而 1.5MB 输出会把面板刷得极快,末屏停在哪取决于终端刷新节奏和机器快慢。
脚本历来用 `|| true` 容忍它。
**2026-09-07 收尾时把它的输出口径从 `FAIL` 改成了 `SKIP`**(只改措辞,判定逻辑与容忍范围一字未动),
因为以前的日志里会同时出现一行 `FAIL` 和一句「失败 0 条」,自相矛盾、极容易被误读成「有问题没修」。
现在它长这样:

```
    | SKIP  expectlast "退出码"(等了 8000ms)
    | == 不计分 ==(其中 1 条末屏时序断言未命中,按 SKIP 处理)
  SKIP  B3b 1.5MB 中量输出:... 历来 `|| true` 容忍、不计分(理由见脚本内注释)
```

**除 B3b 之外,`.flower/scripts/` 里没有第二处「打 FAIL 但不计分」** —— 已逐个脚本核过:
其余每一处 `FAIL` 都走 `bad()` 计数或直接 `exit 1`。
所以**看到 `FAIL` 就是真有问题**,不要再当成噪音。

> 注:`.flower/artifacts/审计修复.md` §5 的表格与 §7 第 4 条还留着「日志里出现 1 行
> `FAIL expectlast "退出码"`」的旧描述。那份报告是历史留痕,没有改动;口径以本节为准。

## 4. 最大的未验证风险:macOS 一次都没跑过

**全部自动化验证都在 Debian aarch64 容器里完成。这个项目在 macOS 上从未编译、从未运行。**
这是唯一一个无法用现有证据消除的风险,必须由持有 mac 的人跑一次。
权威描述见 `.flower/artifacts/验收审计.md` §6。

首次在 mac 上可能踩到的,按「先炸哪个」排序:

| # | 会踩到什么 | 症状 | 修法在哪 |
|---|---|---|---|
| 1 | **自带 ncurses 版本旧**(Apple 是 5.7 系),头不主动给出宽字符原型 | `error: use of undeclared identifier 'get_wch'` / `add_wch`,或 `cchar_t` 未声明 | `Makefile:34` 已备好注释掉的 `# CPPFLAGS += -D_XOPEN_SOURCE_EXTENDED`,去掉 `#` 即可。README **§9「macOS 首次编译报错」**第 1 行 |
| 2 | **`-lncurses` vs `-lncursesw`** | Darwin 分支链的是 `-lncurses`(Linux 分支才是 `-lncursesw`)。若链错,中文宽度算错或直接链接失败 | `Makefile:25-38` 已按 `uname -s` 分支处理,但**这条分支从未实测**。README §9「中文乱码 / 宽度错位 / 光标跳位」 |
| 3 | **`brew --prefix ncurses` 分支** | 装了 Homebrew ncurses 时会优先走 brew 的 `-I`/`-L`;混用 brew 头 + 系统库(或反之)会出诡异符号问题 | `Makefile:26-30`。若可疑,`brew unlink ncurses` 后重来,或手动 `NCURSES_PREFIX= make` |
| 4 | **`KEY_S*` 键码数值** | `make tests` 阶段 `static_assert failed: KEY_SHOME == 391`(或 `KEY_SEND` / `KEY_BTAB`)直接炸 | `src/keys.cpp` 里的 `kNcS*` / `kNcBTab` 是**手抄的数值镜像**(见 `.flower/notes/跨模块约定.md` §3),改成 `make tests` 报出的实际值。README §9「macOS 首次编译报错」第 2 行。这个 static_assert 存在的意义就是让问题在编译期红,而不是运行期表现成「某个键没反应」 |
| 5 | **GNU make 3.81** | macOS 自带 `make` 就是 GNU make 3.81。`filter-out` / 静态模式规则它都支持,但 `make debug -j<N>` 在 3.81 上**没跑过** | 见 `.flower/artifacts/审计修复.md` §7 第 1 条。真出问题就串行 `make debug` |
| 6 | **`setrlimit(RLIMIT_CORE, 0)` 禁 core** | `Ctrl-R` 跑挂的程序在 macOS 上可能仍留 core(语义略有差异),**无任何实测证据** | `src/proc.cpp::childMain`。`验收审计.md` §6 表格最后一行明确标注「无实测证据」。不影响信号汇报 |
| 7 | F 键 / Alt 键(次要) | Terminal.app 的 `kf1` 可能是 `\E[11~` 而非 `\EOP`(F1 打不开帮助);Option 需勾「作为 Meta」否则 `Alt-1..4`/`Alt-0` 失灵 | README **§4.8**(F 键只是别名,不影响主流程)与 **§4.9**(Alt 怎么发);另见 README §9「方向键 / Alt / Backspace 失灵」 |

## 5. 已知的设计取舍(不是 bug,别以后当 bug 修)

完整清单在 **README §10「已知限制」**(30 条),那里写的都是「已知且有意接受」的。
最容易被以后的自己误当成 bug 的几条:

1. **没有选区。** 块操作只有行级快捷键(`Ctrl-K` 剪切行 / `Ctrl-D` 复制行 / `Ctrl-V` 粘贴行,
   `Ctrl-K` 连按会累积多行)。内部剪贴板不通系统剪贴板。(README §10 第 5、6 条)
2. **只编译当前打开的单个文件。** 这是需求边界,不是没做完 —— 没有多文件链接、没有工程。
   (README §10 第 10 条)
3. **原始字符串 `R"delim(...)"` 跨行时高亮是近似的。** 自定义 delim 且体内含 `)"` 会让高亮提前结束;
   单行的高亮状态只有 1 字节,放不下完整 delim 匹配。(README §10 第 1 条)
4. **CRLF 文件保存后变成 LF。** 加载时 `\r\n` 一律规范化为 LF(行**中间**孤立的 `\r` 原样保留),
   保存一律写 LF。`TextBuffer` 里没有存换行风格的地方,还原不了。(README §10 第 8 条)
5. **DNS 解析阶段不可被超时打断。** libcurl 线程化解析器的限制:`CURLOPT_TIMEOUT_MS` 打不断
   一次正在进行的 `getaddrinfo`。首次请求最慢要等满系统 DNS 超时(冷缓存实测约 3.2s)。
   两条硬保证不受影响:请求一定会返回、**它只发生在后台 worker 线程,不卡 UI**。(README §10 第 18 条)
6. **流式下没有 token 计数。** 不解析流式响应末帧的 `usage`,`stream: true` 下
   `prompt_tokens`/`completion_tokens` 保持 0。非流式路径正常。(README §10 第 19 条)
7. **输出撞到硬上限时看不到退出码。** stdout/stderr 各超 `run_output_limit`(默认 1 MiB)后截断;
   再往上到硬上限(`4×limit`,**至少 8 MiB**)会直接杀进程 —— 防「死循环里 printf」吃光内存。
   被杀掉的进程自然就没有正常退出码可显示。(README §6.4 第 3 条)
8. **切模式不会自动触发一次补全。** 这是 P1(空转烧钱)修复的有意取舍:只有 `noteActivity()`
   之后才允许下一次自动请求。想要「切到写代码模式立刻来一发」,把 `setMode()` 里那行 `store()`
   删掉即可,代价是纯空转口径从 1 次变 2 次。(`.flower/artifacts/审计修复.md` §1「副作用与取舍」)
9. 顺带一提,AI 报错(500 / 超时 / 401)之后也**不会自动重试** —— 额度已被那次请求用掉,
   要重试就再打字或按 `Ctrl-A`。有意的,避免「错误 + 限流」变成烧钱循环。

## 7. 如果要继续开发

**建议 1:头文件冻结这个约定,现在可以放松成「改要留痕」,但不要直接废掉。**
`.flower/notes/跨模块约定.md` §0 写的是「`src/*.h` 在 Wave 1 已冻结,任何签名/字段变更
必须由协调者统一改」。那条纪律是为**多 agent 并行**服务的 —— 防止几个人同时改同一个头、
互相把编译搞崩。现在只有你一个人维护,「必须由协调者统一改」已经没有意义了。
但**它顺带带来的两个好处要保住**:

- `make check-headers`(每个头必须自给自足)是个真门,**别删**。
- `artifacts/architecture.md` 是接口权威。**改了头文件就同步改它**,
  否则三个月后你会同时拿到两份互相矛盾的接口描述 —— 这正是 `wave4-app.md` 现在的处境。

所以新约定:**改 `src/*.h` 可以,但必须(a) 跑 `make check-headers`,
(b) 同步更新 `architecture.md`,(c) 在 `跨模块约定.md` 末尾追加一条「为什么改」。**
`审计修复.md` 就是照这个规矩做的:它只在 private 区加了 1 个成员 + 1 个常量,
没动任何已有公开签名,并写明了。

**建议 2:读代码的顺序。**

1. `notes/需求.md` —— 先知道边界在哪,免得实现一个「需求里明确不做」的东西。
2. `notes/跨模块约定.md` —— 21+ 条,**动手前必读**,读它比读代码省时间。
3. `artifacts/architecture.md` —— 接口权威,对照 `src/*.h` 看。
4. `artifacts/验收审计.md` §1 + §7 —— 知道哪条验收标准是靠什么保证的,
   免得改掉一个「看起来没用」的结构(比如练习模式那个「唯一 sink 决策点 + 唯一 switch +
   唯一咽喉点」的结构性保证,那不是过度设计,是验收 7 的证据)。
5. 然后再进 `src/`:`main.cpp` → `app.cpp`(总装)→ 具体模块。

**建议 3:动手前先跑一遍 §2 的第 1、2 步,拿一个「改之前是绿的」的基线。**
改完再跑同样两条,差异就是你造成的。别攒到最后再跑。

**建议 4:交付前唯一的硬门槛还是 macOS 真机验证(§4)。** 在那之前,
任何「已通过」都要读成「在 Debian aarch64 上已通过」。
